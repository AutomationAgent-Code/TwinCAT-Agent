# TwinCAT Agent 产品化计划

> 目标:把当前"可自用的 XAE 内嵌 AI 助手"打造成**可对外销售**的产品。
> 现状基线(2026-07):VSIX 面板已在 TcXaeShell 15.0 跑通,后端 = claude-agent-sdk
> over WebSocket + tc-mcp(COM/PowerShell 桥)+ ba-docsearch,支持多 Provider、
> 权限模式、按项目历史、跟随当前方案。**这是一个能演示的原型,不是一个能卖的产品。**

---

## 0. 先认清差距(原型 → 产品)

| 维度 | 现在 | 产品要求 |
|------|------|----------|
| 安装 | 手动 VSIXInstaller + 注册表 + 管理员拷文件 + 手动起 Python | 一个签名安装包,双击装好,零手动步骤 |
| 运行时 | 裸 Python 3.14 + 一堆 pip 依赖 | 打包运行时(嵌入式 Python / PyInstaller / 服务) |
| 大脑 | 复用**你个人**的 Claude Code 登录 | 合法的商用授权(见 §3,**头号闸门**) |
| 数据 | PLC 代码直发云端 LLM | 明确的数据边界 + 本地模型选项(见 §2) |
| 兼容 | 只验证过这一台(15.0/32位) | 4024/4026 × 15.0/17.0 × 32/64 支持矩阵 |
| 质量 | 能跑,靠手工验证 | 崩溃上报、日志、自动更新、回归测试 |
| 法务 | 无 | 许可协议、隐私政策、第三方依赖合规 |
| 支持 | 你自己 | 文档、工单、版本维护承诺 |

**结论:能演示 ≠ 能交付。下面的计划里,真正耗时的是安装工程化、授权合规、数据边界,不是 AI 功能。**

## 1. 三个必须先拍板的战略决策(每个都改变整个计划)

### 决策 A — 目标市场:中国 vs 国际
- **中国**:客户多用 DeepSeek/通义/智谱(数据出境敏感、成本低);竞品是**倍福中国自带的 coAgent(Qwen3-Max)**——平台方即对手,可能免费捆绑。合规看等保/数据出境。
- **国际**:客户接受 Anthropic/OpenAI 云;竞品少;但 Anthropic 商用条款更严,GDPR。
- **建议**:先中国、聚焦"比倍福自带 coAgent 更强的工程自动化能力"(它主要是问答,你有 tc-mcp 能真正改代码/部署),用第三方国产模型压成本。

### 决策 B — 数据边界:云 vs 本地(决定能不能卖给大客户)
- 机器制造商对 **PLC 源码外传** 极度敏感,很多直接一票否决云方案。
- 三档产品形态:
  1. **云版**(默认):接 DeepSeek 等,便宜、能力强,卖给不敏感的中小客户。
  2. **私有网关版**:客户自己的 Anthropic 兼容网关/自建 vLLM,代码不出厂区。
  3. **纯本地版**:本地跑开源模型(Qwen-Coder 等)+ 本地 RAG,完全离线。溢价最高、能力打折。
- **建议**:架构上"模型可插拔"你已经做到了(多 Provider),把它作为**卖点**:同一产品,三种部署,分档定价。

### 决策 C — 商业模式
- 按坐席订阅(¥/工程师/月) · 永久授权 + 年维护 · 按项目 · OEM 授权给集成商。
- **建议**:订阅制(SaaS 心智)+ 私有/本地版走永久授权+年维护(工业客户习惯买断)。
- **成本透传**:云版把 LLM token 成本转嫁给客户(客户填自己的 Key),你只收软件订阅——**规避你替客户垫 API 费的风险**,也顺带解决 §3 的授权问题。

## 2. 阶段计划

### P0 — 合规与可行性闸门 ✅ 已完成(2026-07)
**已拍板的决策(锁定 P1 走向):**
- **大脑**:claude-agent-sdk **不可**商用嵌入分发 → **P1 必须换成自研 agent 循环**(直调各家 API)。这是 P1 关键路径 + 最大技术风险。
- **模型接入**:**只允许客户自带 Key**,产品不内置任何厂商 Key。合规与费用归客户。
- **首发形态**:**云版**(客户自带云 Key)。私有/本地档后置。
- **目标市场**:**中国 + 国际都要**,同一产品配置区分 ⇒ 自研大脑的 Provider 适配层必须同时支持 **OpenAI 兼容**(DeepSeek/Kimi/GLM/Qwen…)和 **Anthropic 原生**(Claude)。

### P1 — 可交付的 MVP(把原型变成能装的东西)

#### P1-A 自研 agent 大脑(关键路径,先做)
把 claude-agent-sdk 从 `tc_agent/backend.py` 拆掉,自己实现 agent 循环。**好消息:顺带消灭一整类现有 bug**——exit 129(claude CLI 子进程崩)、中毒会话 resume、依赖个人 Claude Code 登录、harness 环境变量剥离 hack,全部随之消失,因为消息数组和循环都归你掌控。
组件拆解:
- [ ] **Provider 适配层**:统一接口,两种后端——
  - **OpenAI 兼容**(chat/completions + function calling):DeepSeek/Kimi/GLM/Qwen/OpenAI 都支持,作为主力通用协议。
  - **Anthropic 原生**(Messages API + tool use):Claude。
  - 客户在 Provider 管理器里填 base_url + key + model + 协议类型(现有多 Provider UI 基本够用,加一个"协议"字段)。
- [ ] **agent 循环**:组装 messages + 工具 schema → 模型返回 tool_calls → 执行 → 回填结果 → 循环到最终文本;流式转发(assistant_text / tool_use / tool_result / result+用量成本)。协议差异封在适配层内,循环本身与厂商无关。
- [ ] **工具层去 MCP 化**:现在 tc-mcp 走 MCP 协议只是因为 claude-agent-sdk 要消费 MCP。自研循环**直接调 `tc_template` 的函数**并生成工具 schema 即可,**砍掉 MCP 中间层和 tc-mcp 的 .mcp.json**,栈更短更好打包。ba-docsearch / RAG 保留为直接调用或 HTTP。
- [ ] **权限门**:plan/ask/accept/auto 重实现——现在归你控制循环,执行工具前判一下即可,比之前接 can_use_tool 更简单可靠。
- [ ] **会话持久化**:你已存整份 transcript;自研后"恢复"= 把存的 messages 重放进下次请求,**不再有不透明 session_id,也就没有中毒会话问题**。
- [ ] **成本核算**:从 API 响应的 token usage 自己算,按厂商价目表。
- 保留最小文件工具(在当前解决方案目录内的 Read/Grep)按需,别复刻整套 Bash/Edit。
- 产出:后端不再依赖 claude-agent-sdk / claude CLI / 个人登录,纯 API + 客户 Key。

#### P1-B 部署工程化(可与 A 并行)
- [x] **一键安装包（测试版）**:单文件 Setup + 嵌入式 Python + XAE 扩展 + 文档库 + 图形启动/卸载；双击安装，仅复制扩展时弹一次 UAC。正式版仍需代码签名。
- [ ] **后端做成 Windows 服务或托盘应用**(替代现在的 Startup .vbs),带自启、崩溃自恢复(自愈逻辑已有,产品化)。
- [ ] **代码签名证书**(EV 或 OV):OT 环境不装未签名扩展。这是硬成本(¥数千/年)。
- [ ] **首启向导**:选 Provider、填 Key、选默认模型。
- [x] **License 校验**:TwinCAT System ID + RSA 离线签发，并提供供应商授权记录查询。

#### P1-C 双市场配置
- [ ] Provider 预设分区:中国区默认 DeepSeek/通义/GLM,国际区默认 Claude/OpenAI。
- [ ] 隐私/数据处理说明按区出(等保口径 vs GDPR 口径)。
- 产出:能发给种子客户装在**他们机器**上、纯客户自带 Key 的 0.9 版。

### P2 — 商业化基建
- [ ] 官网 + 产品页 + 试用申请;演示视频(录一个"一句话生成并部署一个轴控程序")。
- [ ] 定价页 + 三档(云/私有/本地)。

### P3 — 规模化与护城河

## 3. ⚠️ 头号闸门:大脑的商用授权 — 已定性(P0 结论)

**结论:claude-agent-sdk 不可商用嵌入分发 ⇒ P1-A 换自研 agent 循环;模型一律客户自带 Key。** 下文保留背景。

**现在的"登录"档复用你个人 Claude Code 订阅登录——这个模式不能用于卖出去的产品。**
- Anthropic 订阅登录用于商业再分发几乎肯定违反其 ToS;商用需走 Anthropic API(按 token)或商用条款。
- **解法(也最省事)**:产品**不内置任何厂商 Key**,让**客户自带 API Key**(你已经做了多 Provider + 填 Key 的 UI)。这样:
  - 你卖的是"软件 + 工具编排 + 工程自动化能力",不转售模型;
  - LLM 费用与合规由客户承担;
  - 中国客户用 DeepSeek/通义,国际客户用 Anthropic/OpenAI,各自合规。
- claude-agent-sdk 本身的商用许可也要确认(它是否允许被嵌入商用产品分发)。**若不允许,可能要把大脑从 claude-agent-sdk 换成直接调各家 API 的自研 agent 循环**——这是潜在的大改,P0 必须查清。

其它第三方依赖也要过一遍商用许可:WebView2(可商用分发)、pywin32、websockets、你打包进 VSIX 的 DLL 等。

## 6. 最大的几个风险(诚实清单)

1. **平台方即对手**:倍福有自己的 coAgent,可能免费捆绑甚至封第三方扩展。你的生存空间是"做它做不到的闭环工程自动化"。
2. **授权/合规**:见 §3,处理不好整个商业模式不成立。
3. **数据信任**:PLC 代码上云是很多客户的红线,本地/私有档不是可选项而是必需项。
4. **安装工程化被低估**:把注册表 hack + 手动步骤变成一键签名安装,工作量常被严重低估。
5. **支持矩阵**:TwinCAT 版本 × 壳代 × 位数碎片化,你已经踩过,规模化后是持续成本。
6. **一个人做产品**:开发、销售、支持、合规——早点想清楚哪些外包/找合伙人。
